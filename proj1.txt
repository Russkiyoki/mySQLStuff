CREATE DATABASE IF NOT EXISTS electronicsDB;
USE electronicsDB;

CREATE TABLE Suppliers(
	SupplierID INT PRIMARY KEY AUTO_INCREMENT,
	SupplierName VARCHAR(50) NOT NULL,
	Phone VARCHAR(20),
	Email VARCHAR(60) UNIQUE
);

CREATE TABLE Products(
	ProductID INT PRIMARY KEY AUTO_INCREMENT,
	ProductName VARCHAR(100) NOT NULL,
	UnitPrice DECIMAL(10,2),
	Qoh INT DEFAULT 0,
	CategoryID INT,
	SupplierID INT,
	FOREIGN KEY (CategoryID) REFERENCES Categories(CategoryID),
	FOREIGN KEY (SupplierID) REFERENCES Suppliers(SupplierID)
);

CREATE TABLE Customers (
	CustomerID INT PRIMARY KEY AUTO_INCREMENT,
	CustomerName VARCHAR(100) NOT NULL,
	Phone VARCHAR(20),
	Email VARCHAR(60)
);

CREATE TABLE Categories(
	CategoryID INT PRIMARY KEY AUTO_INCREMENT,
	CategoryName VARCHAR(50) NOT NULL
);

CREATE TABLE Orders(
	OrderID INT PRIMARY KEY AUTO_INCREMENT,
	CustomerID INT NOT NULL,
	OrderDate DATE NOT NULL,
	OrderTime TIME NOT NULL,
	FOREIGN KEY (CustomerID) REFERENCES Customers(CustomerID)
);

CREATE TABLE OrderDetails (
	OrderID INT,
	ProductID INT,
	Quantity INT NOT NULL,
	PRIMARY KEY (OrderID, ProductID),
	FOREIGN KEY (OrderID) REFERENCES Orders(OrderID),
	FOREIGN KEY (ProductID) REFERENCES Products(ProductID)
);

There are multiple forms of normalization,
the default and standard being the third form of normalization.
Each form of normalization is another step
towards a cleaner and easier database to maintain.
It becomes easier because you won't have to deal with
updating the same information across many tables,
or with fields in your tables that are hectic and unorganized,
and much more.
Each form of normalization keeps all previous rules
and adds another rule on top of it.

The first form of normalization
is for each field to contain a single value.
An example of someone breaking this rule
would be to insert multiple phone numbers
under the same "phone" field for the same individual / record.

The second form of normalization
is for every single other field rely on the whole key
and not just a part of it.
This means if, for example, we have our OrderDetails table
with a composite key of OrderID and ProductID,
but decided to also have the product's name on it,
then the name would only need to know the ProductID
and not the OrderID
resulting in a partial dependency breaking 2nf.

The third form of normalization
is for every field only rely on the primary key
and nothing but the primary key,
ensuring that there are no transitive dependencies.
If B relies on A, and C relies on B,
that is an example of this transitive dependency.

The design in the ERD follows the third form of normalization.
It adheres to the rules of the first form of normalization
because there are no repeating fields or lists in the values.
Each field has one value for each entry.
It follows the second form of normalization
because all fields solely rely on the candidate or primary key.
For example, in my OrderDetails table
we have a dual primary key, or a composite key.
The Quantity represents how many of said product the customer wants,
and it is fully reliant on which order was placed via OrderID
and which product via ProductID.
It adheres to the third form of normalization
because there are no transitive properties.
Every single value that is not the primary key,
fully relies on the primary key ensuring 3nf.

Denormalization is reintroducing some redundancy into the table
to get faster queries.
You sacrifice some structure to speed up queries
or to skip some joins that would take longer.
An example of denormalization for this database
would be to keep OrderAmount that I took out.
I took it out because it is reliant on 2 fields,
such as quantity and the price of the product.
If we kept it, we would get faster queries
by not needing to calculate the order amount every time,
but sacrifice structure.
